# PEHANLY — Critical bug fixes (shipping, customer login, manufacturing catalog)

Verified locally only (no MongoDB, no deployed Vercel/Render access from the build environment). Nothing here was verified in production.

## Bug 1 — "Add rider name and rider phone number before marking the order as shipped"
* **Root cause (admin UI, reproduced in a browser first).** The rider/courier fields live in their own form with their own *Save shipment* button. *Apply* (status → Shipped) sent only `{status}`. The backend validates the **saved** `order.shipment`, so typed-but-unsaved details were always "missing". Backend validation, field names, persistence and merge logic were correct (pinned by new tests).
* **Fix (`fe/src/pages/OrdersPage.jsx`, new `fe/src/lib/shipment.js`).** Moving to Shipped now (1) validates the form with the backend's own rules and reports exactly what is missing, (2) saves changed shipment details first and stops if that fails, (3) only then sends the status change. A synchronous guard + disabled buttons prevent duplicate submissions (one shipment save, one transition). Karachi never needs a waybill/tracking URL; outside Karachi courier + waybill are still required. The backend is unchanged for this bug.
* **Tests.** Admin: `shipment.test.js` (rules mirror backend), browser `e2e/orders-ship.mocked-api.cjs` (fails before the fix, 10/10 after). Backend: `order-shipping-regression.test.js` over real HTTP (save persists in the shape the Shipped check reads, merge, idempotent re-save, bad phone → 422, courier rules, delivered/cancelled locked).
* **Not covered locally:** the real Shipped transaction (stock commitment, status history) needs MongoDB; that code is unchanged.

## Bug 2 — customer sign-in returns to the Sign In page
* **What was proven.** Against a mock that behaves like the cookie session, two real defects existed in the website: (a) if login succeeds but the browser does not keep/send the HttpOnly `pl_session` cookie, the next request is a 401 and the customer is silently bounced back to Sign In with no explanation; (b) a temporary failure of `/auth/me` on page load (API cold start, timeout, 5xx) was treated as "signed out" even with a valid cookie. Also: per-call `onSuccess` callbacks never ran after sign-in (the portal unmounts), so the welcome toast and any return redirect were dead code.
* **Most likely production cause (NOT confirmed — no access to your deployment).** Website on Vercel and API on Render are different *sites*. The backend default `COOKIE_SAMESITE=lax` makes browsers drop the cookie on cross-site requests, which produces exactly the "login looks fine, then back to Sign In" symptom. The API now logs a startup warning when production + `lax` + a public website origin; set `API_PUBLIC_URL` (Render sets `RENDER_EXTERNAL_URL` itself) for a precise check.
* **Fixes.** Website: login is confirmed with `/auth/me`; if the cookie was not kept the customer sees a clear message instead of a bounce (`SESSION_NOT_PERSISTED`); session restore retries transient failures (only 401/403 mean signed out); `?next=` returns the customer to the page they came from (same-site paths only, never `/account`); sign-in side effects use `mutateAsync`. Backend: startup cookie self-check (`src/utils/cookiePolicy.js`), `.env.example` guidance. Unchanged: HttpOnly cookie sessions, no tokens in storage, genuine 401s still sign out, CORS stays an exact allow-list.
* **Deployment (required if your site and API are on different sites).** On the API: `COOKIE_SAMESITE=none` (Secure is enforced automatically), `CORS_ORIGINS=https://<your exact website origin>` (and the admin origin), `CLIENT_URL=<website origin>`, `TRUST_PROXY=1` behind Render's proxy, optional `API_PUBLIC_URL`. Redeploy the API, then the website. Alternative that avoids cross-site cookies: serve the API on the same site as the website (custom domain, or a Vercel rewrite of `/api/v1/*` to Render with `VITE_API_BASE_URL=/api/v1`). Browsers that block third-party cookies can still break `SameSite=None`; the same-site option is more robust.
* **Tests.** Website: `session.test.js`, `safeNext.test.js`, browser `e2e/auth-session.mocked-api.cjs` (13 checks: login, refresh, second tab, bad password, logout, cookie-not-kept message, cold-start retry, return-to page, hostile `next` ignored). Backend: `session-cookie-cross-site.test.js` (HttpOnly/Secure/SameSite=None cookie + credentialed CORS for exactly the website origin, foreign origin refused, logout clears with same attributes), `cookie-policy.test.js`.

## Bug 3 — Manufacturing → Catalog → Categories: HTTP 500
* **Root cause (reproduced).** `listAdminCatalog` called `.populate(null, 'name slug')` for the **category** type (only styles/variants have a parent). Mongoose throws on a null path → 500. Styles and variants were not affected on the API; in the dashboard the Styles tab also loads categories for its parent picker, so it looked broken too.
* **Fix (`src/services/manufacturing.service.js`).** Populate only when the type has a parent (`style → category`, `variant → style`). Old records with a missing or dangling parent list normally. No data change; still admin/staff-guarded (`requireModule('manufacturing')`); no mock data.
* **Tests (`test/manufacturing-catalog.test.js`, real HTTP).** All three types load; missing/dangling parents don't crash; invalid types rejected; anonymous 401 / customer 403 / staff without module 403 / `manufacturing.read` 200; create category → refresh shows it, duplicate slug 409. The same tests fail (500) against the original code.
* **Frontend** already shows the error with a *Try again* button and the reference ID; unchanged.
* **Deploy:** redeploy the API only. The reference ID in your report could not be looked up (no log access); the reproduction above matches the symptom exactly.
