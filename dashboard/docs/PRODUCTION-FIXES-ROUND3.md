# PEHANLY — Production fixes, round 3 (New Arrivals, categories, one-image create, customer login)

**Verified locally only.** No MongoDB, no access to your Vercel/Render deployments or real browsers on those origins. Nothing below was verified in production; the production checklist at the end is what remains.

## 1. New Arrivals shows only explicitly flagged products
* **Root cause.** The homepage asked for "the 4 newest products" (`sort=newest&limit=4`), and the catalog API had no New Arrival filter, so unflagged products appeared whenever they were recent. The `isNewArrival` field itself (Boolean, default `false`) and the admin toggle were already correct; the cards even showed the "New" badge only for flagged ones, which is why mixed cards appeared.
* **Fix.** Backend: `GET /catalog/products?newArrival=true` filters on the real field (`isNewArrival: true`); `newArrival=false` returns everything not flagged (`$ne: true`). Never derived from `createdAt`. Website: the homepage requests `newArrival=true` and also re-checks `isNewArrival === true` client-side; the section hides when nothing is flagged. "Shop all" and the hero fallback open `/shop?newArrival=true` (new filter chip + "New Arrivals" heading). React Query keys include the params, so toggling the flag shows after the next fetch (default stale window; no manual cache purge needed). Products are not cached server-side.
* **Database/migration.** None. Existing products without the field behave as `false` (the filter matches `true` only).

## 2. Shop by Category shows top-level categories only
* **Root cause.** The homepage rendered every category returned by the API and ignored `parentId`.
* **Fix.** `GET /catalog/categories?parentOnly=true` filters on the schema's `parentCategory` (null or missing). The server-side 60s cache key now includes `parentOnly` so the two views never mix. The homepage uses it plus a defensive `!parentId` filter. Parents still link to `/shop/<slug>`; the full tree (without `parentOnly`) is unchanged, so sub-categories remain in category/shop pages. No names or IDs are hard-coded.

## 3. Product creation: one main image
* **Scope (as requested): creation only.** The one-image limit applies to the create wizard (`productId` unset) and to `POST /admin/products`. **Editing an existing product is unchanged** (up to 25 images, `PATCH` unchanged). Consequence: a hand-made `PATCH` with several images is still accepted by design. Existing multi-image products are untouched and their card cover is still `generalImages[0]`.
* **Frontend.** `ImageGalleryUpload` has a `single` mode: one preview (not distorted, `object-contain`), "Replace image", "Remove image", extra files are ignored with a message, and the replacement only takes effect after the new upload succeeds. Validation message if more than one image is present when creating. Storage still goes through the existing backend `/media` → Cloudinary path.
* **Backend.** `createProductBody.generalImages` is `max(1)`; a create request with 2+ images is rejected with a validation error (422). The first image is the product's main image, which Shop cards already display.

## 4. Customer registration/login works in production (Vercel + Render)
* **What the evidence says.** Your capture shows `Set-Cookie: pl_session=…; SameSite=Lax` and correct CORS, yet `/auth/me` carried no `Cookie`. A `SameSite=Lax` cookie set from `pehanly-brand.onrender.com` is not kept/sent by the browser on requests initiated from `pehanly-brand-2qog.vercel.app` (different sites). So login succeeds, `/auth/me` is 401. This matches the running Render instance having `COOKIE_SAMESITE` at the default/`lax` (the old `.env.example` also shipped `COOKIE_SAMESITE=lax`, which is easy to copy into Render).
* **Audit result (code).** Website uses one Axios instance with `withCredentials: true`; admin uses one too; no other client sends auth requests. Backend order is CORS → cookie-parser → origin guard; login and `/auth/me` use the same cookie name and JWT verification. No code path was found that drops a valid cookie. The earlier website hardening (login confirmed via `/auth/me`, session-restore retry, `?next=`) stays.
* **Fix.** `COOKIE_SAMESITE` is now automatic when unset: in production, if the website origin(s) in `CORS_ORIGINS` are a different site than this API (`API_PUBLIC_URL`, or `RENDER_EXTERNAL_URL` which Render sets itself), the cookie is issued `HttpOnly; Secure; SameSite=None`. Same-site custom domains, localhost and non-production stay `Lax`. An explicit value always wins (and still triggers the startup warning if it is wrong). The startup log now prints whether the value was `env` or `auto`. Unchanged: HttpOnly, no tokens in storage/JSON, exact CORS allow-list (no wildcard), `csrfOrigin` check, logout clears with identical attributes.
* **Caveat — third-party cookies.** `SameSite=None` fixes the Lax problem but browsers that block third-party cookies (Safari/ITP by default; Chrome/Firefox in strict or incognito settings) can still refuse a Vercel↔Render cookie. Customers on those browsers will see the "session was not kept" message rather than a silent bounce. The robust fix is same-site hosting below.
* **Recommended final architecture (documentation only; nothing was changed in DNS/domains).** Storefront `https://pehanly.com` (Vercel) and API `https://api.pehanly.com` (Render) share the registrable domain, so the cookie is first-party:
  1. Render → Settings → Custom Domains → add `api.pehanly.com`; at your DNS add the CNAME Render shows (e.g. `api` → `pehanly-brand.onrender.com`); wait for the TLS certificate.
  2. Vercel → add `pehanly.com` / `www.pehanly.com` per Vercel's DNS instructions.
  3. Render env: `CORS_ORIGINS=https://pehanly.com,https://www.pehanly.com[,https://admin.pehanly.com]`, `CLIENT_URL=https://pehanly.com`, `API_PUBLIC_URL=https://api.pehanly.com`, `TRUST_PROXY=1`. With `COOKIE_SAMESITE` unset this resolves to `Lax`; optionally set `COOKIE_DOMAIN=.pehanly.com` only if the admin on a sub-domain must share the session (leave unset otherwise).
  4. Vercel env: `VITE_API_BASE_URL=https://api.pehanly.com/api/v1` (and the same for the admin project), then redeploy.
  5. Remove the `*.vercel.app` origin from `CORS_ORIGINS` once the custom domain is live (keep it while testing).
